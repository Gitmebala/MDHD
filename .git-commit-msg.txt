Fix calls getting stuck on "reconnecting" after any network blip

Root cause: joinCall() emitted 'join' exactly once, right after creating the
socket. Socket.IO auto-reconnects after a network blip (WiFi<->cell handoff,
weak signal, backgrounding) on its own, but the server treats that reconnect
as a brand-new session and had already evicted the client from the room the
instant the old transport dropped. The client never re-emitted 'join' after
reconnecting, so it was stuck outside the room forever while showing
"reconnecting" with nothing actually happening -- this is very likely what
was happening on a real call tonight, since it is a routine mobile-network
event, not a rare one.

Fix, in two parts (both needed -- confirmed by testing, see below):

1. Move the 'join' emit into the socket's 'connect' handler, which fires on
   both the very first connection and every reconnect, instead of emitting it
   once from joinCall(). state.room is already set before the socket exists,
   so this is safe.

2. On 'disconnect', unconditionally tear down our own RTCPeerConnection
   instead of only doing so if it looked unhealthy. The server always tells
   our partner "this peer left" the instant our socket drops (see
   server.js), which makes THEM unconditionally rebuild their connection from
   scratch on our rejoin. Initially this teardown was conditional on our own
   pc's health, which was too clever: end-to-end testing (force-closing one
   side's socket mid-call, twice, before and after this fix) reproduced a
   concrete failure -- the side that kept its still-"connected" pc received
   the other side's fresh rebuilt offer and threw "InvalidAccessError:
   the order of m-lines in subsequent offer doesn't match order from
   previous offer/answer", because a freshly built RTCPeerConnection's
   transceiver order does not necessarily match an old, still-alive one's.
   Tearing down and rebuilding unconditionally on both sides keeps them in
   lockstep. Confirmed working after this change: forced the same socket
   drop mid-call, both sides tore down, rejoined, and reconnected cleanly
   with live video within seconds.

Also investigated adding a TURN relay as a possible fix for NAT traversal
failures, since that was the working hypothesis before the above was found.
Tested four public TURN services (Open Relay, relay.metered.ca, viagenie,
freestun) against the live app -- all four are dead or unreachable right now,
so none were added; shipping an iceServers entry that does not actually work
would be worse than not having one. Documented in the README instead.
